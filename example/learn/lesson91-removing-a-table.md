# Lesson 91 — Remove a table while old apps still run

Removing an entity from the current schema does not immediately delete its table.
A `Drop` migration stops exposing that entity to the new app, while keeping its
complete PostgreSQL table available to old app versions. A separately reviewed
Contract retires those versions and deletes the table and its data.

This first table-removal path requires PostgreSQL `Worker` migration topology.
`Embedded` is refused before installation or migration work begins.

The [complete app regression source](../../compiler/test/test_migration_table_drop_postgres.ml)
contains a notes app with three versions. V1 exposes `Note` and `Archive`; V2 keeps
`Note` and removes `Archive`. The surviving note handlers are unchanged. V1 can
still create, read and edit archive rows while V2 serves notes. V3 demonstrates
that later deployment requires the removal Contract to finish. This lesson's app
is generated by that regression; there is no standalone lesson app directory.

## Declare the logical removal

Use `tesl migrate app.tesl` to freeze the deployed schema before editing
`VCurrent`. Remove `Archive` from the current schema and remove its uses from the
new app. Keep handlers for surviving entities unchanged. Review the generated
migration:

```tesl
migration = Migration {
  from: Schema.Notes.V1
  to: Schema.Notes.VCurrent
  same: []
  fixtures: []
  entities: { Archive: Drop }
}
```

There is no row conversion function: the new schema has no `Archive` row to
construct. There is no backfill or generation advance for this removal. The
worker retains the exact old table, rows, primary key and ordinary indexes.
Surviving note rows keep their existing generation.

Run `tesl check app.tesl` and `tesl test app.tesl`, then deploy the new Worker and
request processes using your existing PostgreSQL role configuration. A fresh
installation with the V2 binary also preserves the complete V1 origin and its
retained table until Contract; it does not silently skip the removal lifecycle.

## Review and execute physical deletion

Generate the Contract through `tesl migrate contract app.tesl --version 2`.
Its reviewed deletion authority names the entity exactly:

```tesl
contract = Contract {
  of: Schema.Notes.Migrate.V2
  drops: [Table Archive]
  tighten: []
  promote: []
}
```

`Table Archive` authorizes deletion of that checked table, including its data.
It does not authorize another table or an arbitrary dependency. After reviewing
that deletion and completing the rollout, run with the Worker login:

```sh
tesl run app.tesl --schema contract V2 --json
```

Contract waits for admitted old writers, retires old versions, and drains old
compatibility readers before removing their physical table. Requests from retired
versions are refused, including requests using otherwise unchanged entities.
Current processes keep serving the surviving schema. The next schema revision
requires this Contract to finish before expansion.

If the process stops, restart the same Contract command. Each physical operation
and its receipt commit together. A retry recognizes a completed table deletion
from its checked receipt; it does not try to lock an already deleted table or
interpret unexplained missing storage as success.

## Dependencies and the initial boundary

Known external dependencies, such as an administrator-created view referencing
`archive`, refuse Contract before publishing its intent or changing its floors.
Remove or migrate that dependency deliberately, then retry. Deletion also uses
PostgreSQL `RESTRICT`: Tesl does not cascade into unrelated objects. If an
administrator creates a dependency after the initial check, the final deletion
can fail after old versions have been retired. The table remains and Contract is
resumable; resolving the dependency does not readmit the retired versions.

The initial supported operation is deliberately narrow:

- Remove one ordinary entity and leave all surviving entities unchanged.
- Keep at least one entity; dropping the last entity is refused.
- Do not combine Drop with another removal, addition or transformation.
- Queue-bearing histories and previously transformed entities are refused.
- A dropped table may have its ordinary initial indexes. A history that added
  concurrent-index jobs to that table needs a separate index retirement lifecycle
  and is refused here.
- Retired entity identities and physical table names cannot be reused later.

The protected format-5 catalog definitions have changed for this lifecycle.
Earlier experimental format-5 definitions fail closed; this feature does not
provide an automatic catalog upgrade. Use a fresh correctly installed catalog
for the example, preserving any existing database and its matching binaries.

The [compiler boundary tests](../../compiler/test/test_migration_table_drop.ml)
check this scope. The [live PostgreSQL regression](../../runtime/go/teslrt/migration_row_table_drop_native_test.go)
exercises overlap, held old transactions, dependency refusal, fresh installation,
physical removal and restart after a committed deletion receipt. These are
separate from the quick application tests; their current execution status belongs
to the migration regression gate.
