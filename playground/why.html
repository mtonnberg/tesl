Why Tesl?

Stay in control as your codebase grows.

Tesl aims to keep development fast as your application grows, whether you code yourself or work with AI agents. Its compiler helps you express and preserve your rules, with clear explanations and suggested fixes to keep you moving.

Let an LLM explore the open-ended parts of a problem. Give precise requirements to the compiler and checks: what must always be true should live in the program’s contracts. That can mean less code to trace during review and more confidence when changing it.

Focus review on the rules that matter

Suppose a large PR adds callers of a function that displays an invoice. Its signature requires evidence that the invoice belongs to the requested customer. Tesl checks that every new caller supplies that evidence.

You review whether the customer check is correct, whether the function requires the right evidence, and whether any of those boundaries changed. You can stop manually tracing that requirement through every caller. Other behavior still needs review and tests: a proof checks the rule you expressed.

The same idea works for a string that must have 3–10 characters and a special character: write and test the validation check, then require its fact wherever that guarantee matters. The compiler checks that those functions receive validated values.

Keep side effects explicit as helpers evolve

Capabilities make operations such as database reads and writes visible in function declarations. The requirement follows calls: if a helper writes to Note, its caller must declare dbWrite Note too. A read-only path cannot quietly gain a write through a helper. Authentication and the application's access policy still need to be designed correctly.

Write SQL the compiler can check

Write queries using the fields in your entity declarations. The compiler checks field names and types, so a misspelled column or incompatible value is caught while you edit. Query results have types too: a single-row lookup returns a Maybe value, making the missing-row case explicit.

The generated SQL uses parameters for values, and the debugger can show the statement and its bound parameters. You can inspect what reaches the database.

Entity declarations connect the schema to your application’s types. Further migration tooling is in development; the schema guide describes what is available today.

Catch currency and unit mix-ups

Money values carry a currency and use exact integer minor units. Physical quantities carry dimensions, so adding a length to a duration is a compiler error. These types make mistakes visible that would look like ordinary arithmetic on raw numbers.

Keep tests beside the behavior they check

Choose concrete assertions, executable documentation examples, properties over generated inputs, HTTP response assertions or load-test budgets. Tests live alongside your code and run through the local CLI. The playground checks their declarations and helps you write them.

Build the backend with less setup

Typed SQL, queues, workers, caching and SSE are integrated with Tesl’s Go runtime. PostgreSQL-backed queues provide retries and dead-letter handling without a separate queue service. During local development, the CLI can manage the project database.

Deployed database-backed applications connect to your PostgreSQL service. The same language constructs cover the database, background jobs and live updates.

Work with a compiler that helps you move forward

The compiler points to the problem, explains the missing requirement and, where available, offers an edit. A missing import can be repaired directly; a missing proof or capability tells you which contract needs attention.

People and coding agents get the same diagnostic information. The CLI’s agent-context command gives an agent a compact view of errors and declarations, while targeted queries answer questions about types and symbols. An agent can check a change and act on specific feedback.

What if my LLM hasn’t learned Tesl?

It can look Tesl up as it works. The CLI includes the language specification, manual and examples, available offline. An agent can search for an explanation, inspect a function’s signature, try an implementation and use the compiler’s diagnostics to revise it.

tesl help search "proof" searches the documentation; tesl help manual language-spec opens the specification. This gives the agent a local reference and a way to check its work, even when its training data contains little Tesl.

See what happens in production

Tesl gives application code one standard way to log: a structured telemetry event. Add an event where it explains your business behavior; the runtime carries the request’s trace context with it.

OpenTelemetry integration connects logs, metrics and traces across HTTP, SQL, queues, caching and LLM calls. Configure an OTLP destination and enable tracing to see which query or background operation took the time, with built-in instrumentation for those operations.

The instrumentation comes with Tesl. Choose your collector and observability backend, and set the sampling and retention that suit your application.

Inspect running code with your AI agent

The debugger coordinates a pause across instrumented executions and exposes queues, caches, SSE connections and workers alongside the triggering execution’s locals and SQL. If an execution cannot rendezvous in time, it reports a partial stop. The CLI and MCP interface let a coding agent inspect this state too.

Bring authentication and security checks into the workflow

SSO and sessions, explicit authorization requirements, and an OpenAPI export give you connected tools for building and inspecting an API. The CLI’s DAST workflow uses ZAP to scan a running application against its declared API; scanner credentials can come from environment variables.

You choose the access policy and run the scans against your deployment. These tools help you implement and test that policy; they do not establish that every security requirement has been met.

Deploy Go with familiar hosting tools

Tesl compiles to an inspectable Go application. Build a binary or use tesl build --container to produce a Docker image. It runs as an ordinary process or container, fitting the deployment, monitoring and sidecar patterns you already use for Go services.

The runtime includes HTTP header timeouts, parameterized database queries and connection pooling. These provide concrete security and performance foundations beneath your application code.

Container security tools such as Falco operate at the host and container layer; Tesl does not require a special integration. Configure those tools for your deployment as you would for another Go service.
