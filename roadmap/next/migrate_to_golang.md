# Migrate the runtime target from Racket to Go

## Maintainers update 2026-08-05

I think we should migrate all tests to Go, even for the code that moves into a standard lib. This for two reasons: A. we want to know if these standard libs behaves the same or if we introduce a breaking change with the migration (it is ok but we should know), B. we do not fully just want to take other people's word that the libraries work as intended and have some protection against future updates/malicious updates.

## Requirements (maintainer, 2026-08-04)

Hard requirements for any Go backend, regardless of how the design below evolves:

1. **Test parity.** Every Racket test migrates to Go, before or alongside the port. The new runtime ships with the same or better test coverage. Tests covering code that evaporates into the Go stdlib may be dropped, but each drop is flagged and justified, not silently skipped.
2. **Third-party dependency policy.** No third-party Go libraries except under extraordinary circumstances, and every exception is flagged for explicit decision before adoption. *(Decided 2026-08-04: four exceptions approved — pgx, golang-jwt, go-oidc, otel-go; see "Dependency exceptions" below. The policy still applies to any future addition.)*
3. **Debug-loop parity.** The debugging loop (human and AI agent) including attach-to-running-process must be at least as good as today's. This gates retiring the Racket backend.
4. **Lint-clean emitted code.** `go vet`, `staticcheck`, `gosec`, `govulncheck`, `golangci-lint`, `go test -race`, `goleak`, and `nilaway` must all pass (where applicable) on transpiled output, always — see "Toolchain gates" below for how each one actually plugs in.
5. **Coraza WAF, opt-out.** Evaluate embedding Coraza to harden Tesl apps' runtime, well integrated with the OTel infrastructure — both for protection and to build trust. If it turns out to be pure cost with no upside, skip it. *(Decided 2026-08-04: skipped for now, cheap to add later — see "Coraza" below.)*
6. **Best practices by construction.** Emitted code and the runtime library follow Go performance, security, and style best practices. Since Tesl users never write Go, every "Go developers should…" rule becomes an emitter/runtime obligation — see "Runtime hardening defaults" below.
7. **Mutation-test parity.** Built-in mutation testing must execute each Tesl mutant through the selected backend. Go mutants compile before tests run; a Go compile failure is invalid, never a kill. Baseline tests must pass before scoring, mutation IDs/operators stay backend-neutral, and the Racket/Go reports must agree before Racket retirement.

## Background

First-pass analysis (2026-08-02) of replacing the Racket backend, driven by two goals: raw performance and security. Type safety is the compiler's job and stays unchanged — the whole OCaml pipeline (parser, checker, proof system, capability validation) is untouched by this; only `emit_racket.ml` and the `dsl/` + `tesl/` Racket runtime are in scope.

Rust was evaluated first and rejected: Tesl semantics are GC-shaped (closures, immutable ADTs, uniform values, persistent record updates), so emitted Rust degenerates into `Rc<RefCell<>>` soup that forfeits Rust's performance advantage while keeping all the borrow-checker pain in codegen; rustc's compile time (10–60s per emitted app vs ~1s today) kills the api-test/agent dev loop, which is core to Tesl's value proposition; and Rust's headline gain — memory safety — is not a gain over Racket CS, which is already memory-safe. Rust only wins if hard no-GC tail-latency requirements or embedding appear.

Go fits where Rust didn't, and a portability survey of the actual runtime confirmed feasibility: the runtime uses **no `call/cc`, no runtime `eval` of user code** (breakpoint conditions go through a hand-written evaluator, `eval-bp-condition` in `dsl/debug/checkpoint.rkt`), and `dynamic-require` only for module-cycle breaking (`dsl/web.rkt:2465`, `dsl/otel.rkt`, `tesl/agent.rkt`) — trivially replaced by direct linking. Continuation marks appear only in error paths. Nothing exotic blocks a port.

Other contenders, for the record: **OCaml** is the strongest technical fit (one toolchain, full exhaustiveness checking on emitted code, `zarith` solves the Int question natively) but its HTTP/TLS/crypto ecosystem lacks Go-stdlib audit depth; **.NET/F#** is the strongest "boring industrial" alternative (Kestrel perf, audited crypto, `BigInteger`, Native AOT) but carries platform weight and no infrastructure-culture credibility. This mattered while Int semantics were open — a bignum Int seemed to tighten the race toward OCaml vs .NET — but the hybrid-representation decision (see Decisions) neutralizes it: Go carries bignum Int at near-native fast-path cost using `zarith`'s own design, so the race stays settled on Go.

## Why Go

1. **Battle-tested "for free".** A Tesl app becomes "plain Go underneath": `net/http` serving, `pgx` pooling, stdlib `crypto/*` and TLS. The load-handling question stops being "can Tesl scale?" and becomes "can Go scale?" — already answered in every ops team's head. The pool-lease (#31) and SSE-channel (#32) bug classes get outsourced to code with millions of deployments. The ops story transfers too: pprof, delve, `govulncheck`, standard k8s probes — an SRE can operate a Tesl app with knowledge they already have.
2. **Typed target verifies the emitter.** Emitted Racket is untyped; past emit bugs (newtype unwrap miss in `unwrap-non-null`, missing `ECase` arm in `emit_api_test_expr`, secret emitted before its `via` check) shipped silently and were only caught by live testing. Emitted Go is type-checked by the Go compiler — a second, independent verifier of `emit_go.ml` on every build. The static-analysis toolchain (vet, staticcheck, gosec — see "Toolchain gates") extends this: each linter is another independent reviewer of the emitter's output, on every build.
3. **Eject and audit story.** Emitted Go is readable, ownable code: "if Tesl dies you hold a plain Go codebase" de-risks adoption of a niche language, and a security reviewer can actually read the output. Enterprise SAST tooling (CodeQL, Semgrep, commercial scanners) understands Go natively, so customers' existing security pipelines can audit Tesl apps without special support — and some DAST tools are likewise tuned for Go services.
4. **Deployment security.** `CGO_ENABLED=0` static binary → `FROM scratch` image. This subsumes most of `roadmap/later/slimmer_and_more_secure_image_generation.md` (no shell, no package manager, no userland at all — beyond what distroless achieves for Racket) and eliminates that item's bundled-OpenSSL-1.1 supply-chain wrinkle.
5. **Performance.** 2–5x throughput on IO-bound HTTP+SQL workloads, a fraction of the RSS, ms cold start, sub-ms GC pauses. (Honest framing: Racket CS compiles natively via Chez and is not slow; the dominant wins are memory, tail latency, and startup, not raw CPU.)
6. **Dev loop survives.** Go builds small services in ~1–3s; the emit + `go build` + run cycle for api-test roughly matches current Racket timing. This was the Rust killer; Go passes.

## Incremental adoption in Go shops (near-free win)

The transpiler design already solves "how does a Go shop introduce Tesl incrementally" — no FFI needed. A Tesl app compiles to a plain Go service that deploys next to existing services with the same CI, pprof, delve, `govulncheck`, and k8s probes; the service boundary is the integration point, and Go shops overwhelmingly run microservices or at least a handful of services already. This is an adoption argument, not an engineering cost — the work is small ergonomics that make it land:

- Emit a proper `go.mod` and a readable package layout, so the emitted service is a normal module in their monorepo/CI.
- Generate typed Go client stubs for Tesl API endpoints, so neighboring Go services call the Tesl service with a typed client instead of hand-rolled HTTP.
- Optionally: consume existing OpenAPI/proto definitions so the Tesl service can call its Go neighbors typed in the other direction.

**FFI is deliberately not the adoption mechanism.** An arbitrary Go call from Tesl is an unchecked effect — it bypasses the capability system and reopens the fail-open surface closed during 2026-07; every FFI import is an unverified axiom. If FFI ever ships, it comes in two tiers: (1) curated, capability-gated leaf modules first — the existing `*-prim.rkt` lift pattern *is* this model, with the runtime team writing Go leaves and users seeing Tesl modules — and (2) open capability-declared `extern` as a separate decision, only after the Racket backend retires, because any `.tesl` file using Go FFI cannot run through the differential cross-backend oracle (Migration path step 5).

## Architecture: transpiler, not VM

Two textbook routes exist — source-to-source (emit `.go`, shell to `go build`) or a bytecode VM/interpreter written in Go (the Tengo/Gopher-Lua pattern). For Tesl the choice is forced: **transpiler only**. The VM route would be *slower than the current backend* (a tree-walker is 10–100x below native; Racket CS already compiles to native code), loses the Go-compiler-checks-the-emit verification, and kills the "plain Go underneath" credibility (pprof would profile the dispatch loop, delve couldn't step user code). The VM's genuine advantages (hot reload, pause-anywhere) are either unneeded (1–3s builds) or already solved by instrumentation. Interpreter *islands* remain fine and normal — the breakpoint-condition evaluator already is one.

Use Go's **`//line` directives** so emitted code carries `//line foo.tesl:377` — panics, stack traces, and delve then report Tesl source positions natively. This replaces a chunk of what `source_map.ml` + `thsl-src!` do by hand today.

Emitted package layout follows the idiomatic Go shape, because "readable emit" means readable *to a Go reviewer*: `cmd/<app>/main.go` as the composition root (config parsing, pool construction, wiring, server start), one `internal/<module>` package per Tesl module, runtime library under `internal/teslrt` (or a versioned module). The `internal/` boundary is compiler-enforced encapsulation for free. Lifecycle frameworks (e.g. Uber FX) are **rejected** — they violate the thin-runtime invariant; startup/shutdown wiring is a page of explicit code in `main.go`, which is exactly what a skeptical reviewer wants to read anyway.

## The cost center: absorbing the macro layer

The Racket backend leans hard on macros: `define-record`/`define-entity`/`define-checker`/`define-api` (in `dsl/types.rkt`, `dsl/web.rkt`, `dsl/sql.rkt`) expand into codecs, SQL mapping, routing, auth/proof wiring. Go has no macros — **all of that expansion moves into `emit_go.ml`**. Expect the emit backend to grow 2–3x over `emit_racket.ml`'s ~8.7k lines, with the runtime library shrinking correspondingly. This is where the effort concentrates; the HTTP/SQL plumbing is not the hard part.

## Semantic mapping notes

- **Integers**: Int is arbitrary-precision and stays so (see Decisions). Go representation is the hybrid `teslrt.Int` — value struct, int64 fast path, `*big.Int` spill on overflow (`go/constant`'s pattern; stdlib-only, no new dependency). Arithmetic, equality, hashing, and ordering all route through runtime helpers; bare Go operators on the struct are incorrect by construction (wraparound on the int64 field, pointer comparison on the big field), and the lint gate forbids them in emitted code. Full testing mandate and canonical-form invariant in the Decisions section.
- **Records**: today symbol-keyed hashes (`record-value` + `tesl-hash`). In Go: nominal structs — the checker knows every type. Perf win and type-check win. Catch: `tesl-dot/runtime` does runtime structural field resolution with checker hints (the #26/#27 machinery). Go needs 100% static resolution; any remaining runtime-fallback cases must become checker responsibilities. Flushing those out is itself a soundness improvement.
- **ADTs**: sealed-interface or tag+struct pattern via generics. Go does **not** check exhaustiveness — a real loss vs OCaml/Rust. Mitigation decided (see Decisions): both the `exhaustive` linter in generated-code CI (with `default-signifies-exhaustive: false`) and emitted `default: panic` arms (the checker guarantees exhaustiveness upstream, so the arm is unreachable containment).
- **Facts / proofs / capabilities**: runtime values today (`check-ok-facts`, `ensure-named`, `define-capability`, `require-capabilities!`). Port as plain structs + registries. Must be ported faithfully — the migration itself reopens the forgery-class surface closed during 2026-07; treat the capability/proof runtime as the security-critical core of the port, and keep it small enough to audit in an afternoon and array-lookup cheap on the hot path.
- **Recursion**: Racket has TCO, Go doesn't. Recursive `tesl/list.rkt`-style ops become loops in the Go runtime; tail-recursive worker loops become `for`. Mechanical but must be systematic.
- **Concurrency**: threads/queues/SSE map to goroutines + channels, more idiomatically than to Racket threads. Every emitted goroutine follows a leak-safe pattern (owned by a context, cancelled on shutdown) — `goleak` and `-race` in the test harness enforce this structurally (see "Toolchain gates").
- **Cyclic imports — solved by design, not an open decision.** Tesl allows import cycles among pure declarations (cycles containing config decls are already a compile error — `cycle_unsafe_decl_reason`, `compile.ml`). Racket forbids cyclic `require` too, so the emitter already handles this: the cyclic-SCC inliner (`emit_racket.ml`, "Inline declarations from cyclic SCC modules") textually inlines a cycle's declarations into the importing module. The Go mapping is *cleaner*: collapse each cyclic SCC into one Go package with **one file per member module** — files within a Go package reference each other freely (no ordering, no forward declarations), so mutual recursion works without textual inlining, and `//line` keeps each file mapped to its own `.tesl` source. Two mechanical items: module-prefixed name mangling inside merged packages (collision dedup, as the inliner's `emitted_names` table does today), and a seam test that const-*value* cycles are checker-rejected (Go rejects initializer cycles as a loud build error anyway — fail-closed). For the readable-emit invariant, the merged package's comment should say "import cycle collapsed to one package" so a Go reviewer isn't puzzled by two modules sharing a package.

## Float parity (researched 2026-08-12, not yet implemented)

Float is deliberately still fail-closed in the Go backend, because the parity risk is in *formatting and transcendentals*, not in arithmetic. The findings, so the next attempt starts from measurement rather than guesswork:

- **One choke point on the Racket side.** Every observable Float string goes through Racket's `number->string` on a flonum (`tesl/float.rkt` `Float.toString`, `tesl/string.rkt` `String.fromFloat`, and interpolation via `tesl-display-val` → `(format "~a" …)` in `dsl/private/evidence.rkt`). The rule, reverse-engineered and validated differentially: shortest round-trip decimal digits, exact-decimal ties rounded AWAY FROM ZERO; positional layout iff `-3 ≤ dp ≤ max(14, nd+3)` (dp = decimal-point position, nd = digit count), otherwise `d[.ddd]e±E` with an unpadded exponent; always at least one fraction digit (`100.0`); `-0.0`, `+inf.0`, `-inf.0`, and `+nan.0` for every NaN of either sign.
- **A `teslrt.FormatFloat` helper is mandatory.** Go's own `'g'`/`-1` verb is NOT usable: it switches to exponent form at exp ≥ 6, zero-pads exponents to two digits, and prints `1e+07` where Racket prints `10000000.0`. A Go implementation of the rule above (`strconv.FormatFloat(f,'e',-1,64)` for digits, a `big.Rat` tie correction, hand-rolled layout) matched Racket on 450,033/450,033 doubles including subnormals, ±0, ±inf and NaN.
- **Equality is inverted from Go's `==`.** Tesl `==` on Float is Racket `equal?`, so `NaN == NaN` is TRUE and `0.0 == -0.0` is FALSE — both the opposite of Go. `teslrt.FloatEqual` is required; ordering (`< <= > >=`) is plain IEEE in both backends and needs no helper.
- **Literals cannot be emitted bare.** Go untyped constants fold exactly (`0.1+0.2+0.3` → `0.6`, where Racket gives `0.6000000000000001`), Go constants have no negative zero, and typed-constant overflow is a compile error where Racket yields `+inf.0`.
- **Transcendentals are the hard blocker.** `sqrt` is bit-identical, but `sin`/`cos`/`tan` diverge from Racket on 22%/22%/34% of inputs (up to 9,214 ulps), `pow` on 3.4%, `exp` on 0.09%, and Go's `math.Log` is outright wrong for subnormals (`Log(5e-324)` = −709.09 vs the true −744.44). Phase 1 must REJECT `Float.log/exp/sin/cos/tan/pow` in the emitter rather than emit divergent code.
- **No corpus file is unblocked by Float alone** — each of the five Float-touching files has at least one further independent gap — so this slice's payoff is a hand-written differential corpus, not corpus reach.

### Float decisions (maintainer, 2026-08-12): prefer Go where Go is correct

The rule applied below: adopt Go's native behavior, accepting a breaking change, wherever Go's behavior is defensibly correct and the only cost is that Racket printed something else. Keep Racket's behavior only where Go's is *worse*, not merely different. Each item was re-verified directly against go1.26.4, not taken from the survey.

**Adopt Go (breaking, accepted):**

1. **Shortest-digits engine + tie rule.** Use `strconv.FormatFloat(f, 'g', -1, 64)` digits as-is, including Go's round-half-to-even on exact decimal ties. Both engines round-trip; the `big.Rat` tie correction that would have reproduced Racket's away-from-zero rule is deleted before it is written. Visible effect: `168302117738307.13` prints as `1.6830211773830712e+14`.
2. **Layout threshold.** Go's `'g'` rule (positional for `-4 ≤ exp < 21`, exponent form outside it, unpadded-to-two-digit exponent). Visible effect: `1e+07` where Racket printed `10000000.0`, and `1e-05` where Racket printed `0.00001`.
3. **NaN and infinity spelling.** `NaN`, `+Inf`, `-Inf` — Go's spelling, not `+nan.0` / `+inf.0`. Both are arbitrary; Go's is what a Go reviewer expects and it needs no custom runtime code.

**One deliberate deviation from bare Go output:** append `.0` when the formatted result contains neither `.` nor `e` (so `1.0`, `-0.0`, `100.0`). This is not a taste call — Tesl has both `Int` (arbitrary precision) and `Float`, and Go's bare `1` makes a Float indistinguishable from an Int in logs, interpolation, and test expectations. Two lines in `teslrt.FormatFloat`, and it keeps the type visible.

**Keep Tesl/Racket semantics — Go's is worse here, not just different:**

4. **`==` on Float stays structural** (`NaN == NaN` is true, `0.0 == -0.0` is false), via `teslrt.FloatEqual`. Go's `==` is IEEE and therefore "correct" as IEEE, but it is not an equivalence relation: with IEEE equality a record or Dict/Set key containing `NaN` stops equalling itself, so a stored key becomes unfindable and structural record equality loses reflexivity — that reflexivity is also what the checker's reasoning about `a == b` assumes. Postgres independently agrees with Tesl that `NaN = NaN` (it deliberately deviates from IEEE), so keeping this also keeps a DB round-trip consistent. Ordering (`< <= > >=`) is plain IEEE in both backends and needs no helper.
5. **`Float.log` cannot use `math.Log` unwrapped — this is a Go defect, verified.** `math.Log` returns `-709.0895657128241` for *every* subnormal input: `Log(5e-324)` and `Log(2.5e-323)` give the same answer, and both are wrong (true values ≈ −744.44 and −742.83). The fix is a scaling wrapper — `Log(x·2¹⁰⁰) − 100·Ln2` for subnormal `x`, which reproduces both true values exactly — so `teslrt.Log` wraps rather than forwards.
**Why helper calls do not weaken the eject argument.** The point of "if Tesl does not work out you hold a plain Go codebase" is ownership and readability, not using stdlib defaults for every operation: the emitted service is a normal Go module, and `internal/teslrt` is a small package a reviewer can read in one sitting and then own. Equality already goes through helpers for a structural reason — arbitrary-precision `Int` is a struct that is deliberately non-comparable, so `teslrt.Equal` is unavoidable — which makes `teslrt.FloatEqual` uniform with the rest of the emitted code rather than an exception a maintainer would trip over. What genuinely does tax the eject argument is naming: `Tesl_area(tesl_r)` is not what a Go author would have written, and idiomatic names (`Area`, `r`) with mangling only on collision with a Go keyword, builtin, or sibling identifier is worth a slice of its own before the backend is presented as an eject story.

6. **`sin`/`cos`/`tan`/`pow`/`exp` are undecided, and a Racket diff is not the deciding evidence.** The measured 22–34% divergence rate against Racket says the two differ, not which is right; near a zero of `sin`, ulp-of-result exaggerates a small absolute error. Decide by comparing both against a correctly-rounded reference (MPFR-class), not against each other. Until then use Go's `math` and record the divergence as known, rather than blocking the Float slice on it.

### Dependency exceptions (all four approved 2026-08-04)

† Each of these is an approved exception to "no third-party libraries". Provenance, recorded for the audit trail: **none of the four is maintained by the Go team.** A near-first-party tier does exist — `golang.org/x/*` is Go-team maintained (though not under the stdlib compatibility promise), and `x/crypto` supplies bcrypt/argon2, so password hashing barely counts as an exception at all.

- **`pgx`** — community project, maintainer-led (jackc). But effectively **unavoidable**: the Go team ships no PostgreSQL driver; `database/sql` is only the stdlib interface, and `lib/pq` is in maintenance mode. pgx is the de-facto standard (better pooling, binary protocol, richer type mapping). Alternative shape: `database/sql` with pgx as the driver only (`pgx/stdlib`), which keeps the app-facing API stdlib-shaped. The least optional exception on this list.
- **`golang-jwt`** — community org (successor to the abandoned dgrijalva repo). JWT parsing/validation is exactly the code one should not hand-roll (alg-confusion, `none` attacks). Actively maintained, small, widely audited. The considered alternative — hand-written JWS over stdlib `crypto` — was feasible (Tesl only needs a narrow JWT profile) but rejected in favor of the audited library.
- **`coreos/go-oidc`** — CoreOS/Red Hat. OIDC discovery + token verification. Hand-rolling reopens the SSO surface reviewed in 2026-08.
- **`otel-go`** — CNCF-official OpenTelemetry SDK; not Go-team, but the closest thing to industry-first-party on this list. The alternative is porting the hand-rolled ~1.5k LOC OTLP implementation, which preserves exactly the code the migration wants to delete. Least controversial exception.

‡ The earlier draft listed **gomail** for email — rejected: unmaintained since ~2016. `net/smtp` is frozen but functional; Tesl's email surface is narrow (capability-gated send), so a thin hand-written MIME/auth layer over `net/smtp` fits the no-third-party policy better than any ecosystem pick.

Everything else in the table is Go stdlib. Any future dependency proposal goes through the same flag-and-decide gate.

## Pre-migration: lift Racket stdlib into Tesl first

A third bucket exists besides "evaporates" and "ports by hand": Racket runtime code that could be **rewritten in Tesl itself before any Go work starts**. Anything living in a `.tesl` file needs no porting at all — `emit_go.ml` compiles it like user code — and the lifted modules double as differential-corpus material for the cross-backend oracle (Migration path step 5).

The pattern is already proven in-tree: `tesl/list.tesl` and `tesl/either.tesl` compile at build time into `list-derived.rkt` / `either-derived.rkt`, with the hand-written Racket core shrunk to small `*-prim.rkt` leaf modules. The pre-migration work is applying that same lift to the remaining pure-logic modules.

Good lift candidates (pure combinators over small primitive leaves):

- `tesl/dict.rkt` (~270 LOC) and `tesl/set.rkt` (~175) — same shape as list/either: keep the hash-backed leaves (`empty`/`insert`/`lookup`/`member`), lift `insertWith`, `union`, `merge`, and the fold-style ops.
- `tesl/int32.rkt` (~200) — the whole range rule ("closed ⇒ Int32, overflow-possible ⇒ Maybe Int32") is pure logic over Int leaves. Near-ideal lift.
- `tesl/money.rkt` (~470) — explicitly "Pure module: no capability"; exact-integer minor units and half-even rounding lift cleanly. Keep `dsl/private/money-core.rkt` (structs + display) and the generated currency table as leaves.
- `tesl/agent-provider.rkt` (~590) plus parts of `tesl/agent.rkt` (~850) — provider request/response normalization is pure JSON reshaping between provider dialects, and the agent loop's control flow lifts over http/tool-dispatch leaves. This is the single biggest prize: it sits squarely in the "ports by hand" bucket — no Go ecosystem library absorbs it.
- `tesl/jwt.rkt` (~750), partial — claims validation (exp/nbf/iss/aud) and header/payload construction lift; HMAC sign/verify stays a crypto leaf.
- `tesl/tuple.rkt`, `maybe.rkt`, `result.rkt`, and parts of `string.rkt`/`float.rkt`/`int.rkt` — small and mostly leaves already; marginal gain, do opportunistically.

Deliberately NOT lifted:

- `dsl/sso.rkt` and the OTel family (`dsl/otel.rkt`/`traces.rkt`/`metrics.rkt`/`trace-context.rkt`) — the plan above maps these to `go-oidc` / `otel-go`; lifting them to Tesl would preserve hand-rolled implementations exactly where the point is to delete them for battle-tested libraries.
- The proof/capability runtime (`check-runtime.rkt`, `capability.rkt`, `evidence.rkt`) — chicken-and-egg (it enforces Tesl's own guarantees), and the port plan wants it as a small hand-audited Go core anyway.
- `web.rkt`, `sql.rkt`, `queue.rkt`, `http-client.rkt`, the debugger — these ARE the primitives Tesl code sits on.

Rough payoff: of the ~13k non-test runtime LOC in the "ports by hand" half, roughly 2–3k lifts to Tesl. Suggested order: dict/set/int32 (mechanical, proves the pattern scales), then money, then agent-provider/agent (largest win; needs care around tool-dispatch and capability leaves).

Caveat: lifted code goes through the emitter, so Go's no-TCO recursion issue applies to it — but that is a general `emit_go.ml` obligation for user code anyway, so it adds no extra cost.

## Test migration and parity

Requirement 1 made concrete. The Racket-side test estate has three fates:

1. **Migrates as-is (the default).** `tests/*.tesl`, `compile-examples.sh`, the ratchet suites, api-test corpora — these are backend-agnostic by construction and become the differential oracle (Migration path step 5). No rewrite needed; they just run against both backends.
2. **Ports to Go.** Racket unit tests of runtime internals that survive the port (proof/capability runtime, checkers, api-test harness, debugger, domain registry) get equivalent Go tests — written alongside each ported module, not batched at the end. Coverage on the ported module must meet or beat the Racket original.
3. **Dropped, with a flag.** Tests of code that evaporates into the Go stdlib or an approved library (pool internals, hand-rolled OTLP wire format, servlet plumbing). Each drop is recorded with its justification in the migration tracker; "the stdlib is tested upstream" is acceptable, silence is not.

Additionally, Go enables test classes Racket didn't have: the differential corpus runs under `go test -race`, `goleak` verifies no goroutine outlives its test, and native fuzzing (`go test -fuzz`) targets the runtime's parsing edges (JSON codecs, header parsing, the breakpoint-condition evaluator) plus the hybrid `teslrt.Int` spill/normalize paths in scheduled runs. The `teslrt.Int` module additionally carries its own property-based suite and formal review per the Decisions mandate — it is held to the same standard as the capability/proof runtime.

Mutation testing is part of test parity, not a Racket-only utility. `tesl mutate --backend go` uses the same surface-AST mutants as Racket, compiles every emitted mutant before running its generated Go tests, and classifies only an executed test failure as killed. CI runs the lesson42 GDP-boundary corpus through both backends and pins the same mutant count/order and kill result. The Go runner must reject a red baseline before generating a score, use per-mutant timeouts, and report unsupported emit/build states as incomplete failures.

### Estate inventory (measured 2026-08-12)

The numbers behind the three fates, so "parity" has a denominator:

## Debugger and api-test port

Feasible because the current design is **instrumentation-based, not Racket-magic-based**: `thsl-src!` wraps statements with source location + locals; the checkpoint table, control channel, and DAP server are ordinary code. The same technique works verbatim in emitted Go — instrumentation calls checking a breakpoint table, blocking on a channel, control channel over TCP, DAP server in Go. The condition evaluator ports directly. Release builds erase instrumentation exactly as now — and must **provably** do so, or the "plain Go underneath" claim carries an asterisk. Value-tree and the SQL lens are reimplementation work, not architecture loss.

Per requirement 3, parity is a gate, not an aspiration: breakpoints, stepping, locals/value-tree, the SQL lens, attach-to-running-process (control channel + `tesl run --debug` + DAP attach across CLI/MCP/VSCode), and the api-test debug loop must all work at least as well as today before the Racket backend can retire. Write the parity checklist against the current feature set at port time and track it like the test migration.

## Release builds

Design invariant 3 ("zero instrumentation in release builds, verifiable structurally") made concrete. Three candidate mechanisms, one recommendation:

- **Mode-split emit (recommended).** `emit_go.ml` has two modes. Debug mode emits instrumentation calls (breakpoint-table checks, locals capture, control-channel hooks). Release mode emits *none of it* — no import of the debug package, no call sites, no stubs. "Release build" is then structurally defined: emitted source contains zero references to `internal/teslrt/debug`.
- **Build tags** (`//go:build debug` with no-op stubs) — rejected. Instrumentation call sites stay in the source, so a Go reviewer sees hooks threaded through every function: the "plain Go underneath" claim carries exactly the asterisk this invariant exists to prevent. And no-op calls are not guaranteed free.
- **Runtime flag** — rejected outright; instrumentation present and reachable in production binaries.

Verification, three layers:

1. **Structural seam test in CI**: release-emit the full corpus, assert zero references to the debug package (grep or AST check over emitted source). Go's unused-import compile error backstops partial removal — if the emitter drops all call sites but leaves the import, the build fails loudly.
2. **Binary check**: `go version -m` on the built binary must not list the debug package; symbol table likewise.
3. **Mode definition**: `tesl build` emits release by default; instrumentation exists only in `tesl run --debug` and api-test builds. This mirrors the Racket backend's existing expansion-time gate + bytecode mode-marker design, so the CLI surface and mental model carry over unchanged.

## Toolchain gates for emitted code

Requirement 4 made concrete. The gate is: **every emitted app passes the full static-analysis stack, always** — which makes each tool an independent reviewer of `emit_go.ml`, extending the "typed target verifies the emitter" argument. A gosec or staticcheck finding on emitted code is an emitter bug by definition and gets fixed in the emitter, never suppressed per-app.

How each tool actually plugs in (the original note's names were off — none of these are `go` subcommands except vet/test):

| Tool | What it is | Where it runs |
|---|---|---|
| `go vet` | official AST checks (printf verbs, mutex copies, shadowing) | every emit, part of the build gate |
| `staticcheck` | correctness linter (dead code, concurrency misuse, nil derefs) | CI over emitted corpus |
| `gosec` | security AST scanner (SQL string concat, weak TLS, hardcoded creds, `unsafe`) | CI over emitted corpus |
| `govulncheck` | dependency CVE scanner against the Go vuln DB | CI + scheduled (new CVEs appear without code changes) |
| `golangci-lint` | aggregator that runs the above concurrently — the practical CI entry point, with `exhaustive` enabled for the ADT gap | CI over emitted corpus |
| `go test -race` | race detector — needs running workloads, not static scans | differential corpus + Go unit tests run under it |
| `goleak` (Uber) | test *library* asserting no leaked goroutines — must be wired into the generated test harness, it is not a linter | api-test harness + Go unit tests |
| `nilaway` (Uber) | nil-panic prover; pre-1.0, known false positives | advisory lane first; promote to gate if the noise floor allows |

Two practical notes. First, linters false-positive on generated code (unused pattern-match binders, deliberately exhaustive switches with panic defaults); the lint *config* is part of the emitter contract, versioned with `emit_go.ml`, with every disabled check documented — a sprawling ignore file would gut the credibility claim. Second, the gate runs over the whole differential corpus in CI, so a lint regression in the emitter is caught the same way a behavior regression is.

## Hardened build and supply chain

Build hardening, all stdlib-toolchain, on by default for release builds:

- `CGO_ENABLED=0` static binary, `FROM scratch` image (see Why Go, point 4).
- `-trimpath` — strips absolute paths and usernames from the binary.
- `-buildmode=pie` — position-independent executable, enables ASLR. Verify compatibility with `FROM scratch` static linking (PIE + fully static requires care); if they conflict, document the choice.
- Reproducible builds where feasible — strengthens both the audit story and signing.

Supply chain, worth adopting since the dependency set is tiny by policy:

- **SBOM** generation (`cyclonedx-gomod`) as a build artifact — with four-ish dependencies, the SBOM is short and legible, which is itself a selling point.
- **Sigstore cosign** for image signing.
- **OpenSSF Scorecard** on the repo and on each approved dependency — feeds the flag-and-decide gate for exceptions.
- **CodeQL / Semgrep** — primarily a benefit for *users* (their enterprise pipelines can scan emitted Tesl apps natively), but running them in our own CI over the emitted corpus is cheap and catches what gosec misses.
- Google's `ko` for image building — noted, but the maintainer preference is a non-Google-distributed base story, and `FROM scratch` via a plain Dockerfile is trivial anyway. Low priority.

## Runtime hardening defaults

Requirement 6 made concrete. The key structural advantage: Tesl users never write Go, so hardening isn't a best-practices document humans must remember — it's **emitted once, correctly, in the runtime library and codegen, and every Tesl app gets it by construction**. The items below are the distilled obligations (from a longer survey of enterprise Go practice; the survey's human-process advice — code review checklists, DI frameworks — is dropped, and its Uber FX recommendation is explicitly rejected under the thin-runtime invariant).

**Server defaults (`net/http`):**

- Explicit timeouts on every emitted `http.Server` — a zero-value server allows connections to stay open forever: `ReadHeaderTimeout` 2–5s (Slowloris), `ReadTimeout` and `WriteTimeout` sized above handler deadlines, `IdleTimeout` 60–120s. `WriteTimeout` must exceed application-level handler timeouts so structured 503s can still be written instead of raw connection resets.
- Request body caps via `http.MaxBytesReader` before any decode — bounded memory per request, no OOM from a hostile payload. Cap configurable per endpoint from the Tesl side where uploads are legitimate.
- Security headers (HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, CSP) emitted as a ~20-line stdlib middleware — hand-written, not `unrolled/secure`, per the dependency policy. Match or exceed what `dsl/web.rkt` sets today.
- If terminating TLS in-process: `MinVersion: tls.VersionTLS13`, modern curve preferences. (When TLS terminates at the ingress, this is moot but harmless.)

**Code-level obligations (runtime library + codegen):**

- `crypto/subtle.ConstantTimeCompare` for every secret comparison (API keys, HMAC signatures, session tokens) — never `==`. This is a runtime-library obligation in the auth/JWT/secret code paths.
- Error sanitization at the HTTP boundary: internal errors logged structurally with a correlation ID, clients receive generic payloads. Tesl's typed error model already enforces most of this shape; the port must not regress it.
- Password hashing with explicit bcrypt (or argon2id) cost parameters, never library defaults; fresh `crypto/rand` IVs per encryption operation.
- `context.Context` threaded through every emitted handler into DB calls, outbound HTTP, and queue operations; every `context.WithTimeout` paired with `defer cancel()` — a codegen pattern, enforced once in the emitter.
- Mass-assignment is a non-issue by construction: Tesl's typed codecs and checker already separate transport decoding from domain values, which is the DTO/domain-entity discipline Go guides ask humans to maintain manually. Worth stating in the docs as a Tesl advantage.

**Runtime/deploy defaults:**

- `GOMEMLIMIT` set to ~85–90% of the container memory limit in generated deploy configs — without it the GC ignores cgroup limits and the kernel OOM-kills the process. Pairs with the existing image-generation roadmap item.
- `net/http/pprof` exposed on a loopback-only/ops port (never the public listener) — the "SRE can operate it" claim depends on this being on by default and safe by default.

**Performance practices (post-parity, not gate):**

- Slice pre-allocation and `sync.Pool` buffer reuse on hot paths (JSON encoding) — apply in the runtime library where profiles justify it, not speculatively.
- Escape-analysis review (`-gcflags="-m"`) of the runtime's hot paths once real workloads exist.
- **PGO**: Go's profile-guided optimization consumes a production CPU profile (`default.pgo`) at build time for 2–12% fleetwide gains. Interesting Tesl twist: `tesl build` could accept a pprof profile and place it for the Go toolchain automatically — a later, cheap win.

## Coraza (WAF) — skipped for now (decided 2026-08-04)

[Coraza](https://coraza.io) is a Go-native WAF library (ModSecurity/OWASP Core Rule Set compatible) that embeds as `net/http` middleware — no sidecar, no separate process, which fits the single-static-binary story. The original proposal was on-by-default with opt-out, findings surfaced through OTel (denied/flagged requests as span events + metrics).

**Decision: skip.** The case against outweighed the case for at this stage: CRS is tuned for browser-facing HTML apps and false-positives on JSON APIs (Tesl's dominant traffic shape), so it would need a curated ruleset with ongoing maintenance; per-request latency cost; and it would be by far the largest dependency-policy exception ever granted, entering an otherwise tiny go.mod. Much of what a WAF catches, Tesl already prevents structurally (parametrized SQL by construction, typed decoding rejecting malformed bodies).

**Deliberately cheap to reverse.** Coraza is plain `net/http` middleware; the emitted middleware chain keeps a well-defined slot, so adding it later is a runtime-library change plus a config flag — no architectural cost, no emitter changes. Revisit after the port stabilizes if the trust signal ("ships with an embedded OWASP CRS WAF" is legible to security reviewers in a way proof-system arguments are not) turns out to matter for adoption. If revisited, the evaluation procedure stands: prototype behind a flag, run a realistic API workload, measure latency + false-positive rate with a tuned JSON-API ruleset, then decide.

## Design invariants (the credibility claim creates these)

The "battle-tested for free" argument holds only while these stay true — treat them as stated invariants of the backend, not accidents:

1. **Thin runtime.** Lean maximally on stdlib; if a skeptic opens emitted code and finds a thick custom framework between request and handler, the claim degrades to "Go plus a framework you've never heard of."
2. **Readable emit.** Emitted code should look like Go a person could have written, in a layout a Go reviewer expects (`cmd/` + `internal/`).
3. **Zero instrumentation in release builds**, verifiable structurally.
4. **Minimal, explicitly-approved dependency set.** Every third-party library is a flagged, documented exception (see Dependency exceptions); the go.mod of an emitted app should fit on one screen.
5. **Lint-clean emit.** The full toolchain gate passes on every emitted app; lint findings are emitter bugs, and the lint config's exceptions are versioned and documented.
6. **Secure defaults by construction.** The Runtime hardening defaults section is the contract; every emitted app gets all of it with zero user action.

Honest limit to keep in the docs: the credibility transfer covers the *runtime*, not codegen quality — emitted code can still be slow in any language (allocation churn, N+1 queries). Load tests on emitted apps are still needed.

## Decisions (settled 2026-08-04)

1. **Int semantics: Int stays arbitrary-precision; the Go backend uses a hybrid representation.** DECIDED (2026-08-04 — revised the same day; an earlier call to redefine Int as checked int64 was reversed after cost analysis). The Go runtime represents Int as a value struct with an int64 fast path spilling to `*big.Int` only when a result leaves int64 range — the same pattern the Go toolchain itself uses internally (`go/constant`), and the same design as OCaml's `zarith`. Why the reversal:
   - Trap-checked int64 would have needed the same per-op overflow branch the hybrid needs; fast-path cost is equivalent (one predictable branch, ~1–2ns), so the semantic break bought almost nothing.
   - Keeping bignum semantics eliminates what would have been migration step 0 entirely: no Racket-side retrofit, no existing-program breakage, no `NUMERIC`→`BIGINT` column migration (the NT-07 guard in `dsl/sql.rkt` stays true), the `LBigInt` (A9/HM-1) literal machinery stays, and the differential oracle matches by construction.
   - Bounded use cases are already served by Int32 (int4, full companion surface). An explicit Int64 surface type can be added later on the Int32 precedent if profiling shows the 2^31–2^63 band needs compact DB storage.

   Implementation constraints — this module is semantics-critical (a wrong result here is a soundness-class bug sitting under every arithmetic op in every Tesl program):
   - **Canonical-form invariant**: the `big` pointer is non-nil iff the value is outside int64 range. Equality, hashing, ordering, and map-key use must route through runtime helpers — never Go `==` on the struct (pointer field breaks it) and never bare operators on the `small` field (silent wraparound). Tesl already routes equality through helpers, so this is existing discipline, but the lint gate should additionally forbid direct struct-field arithmetic in emitted code.
   - **Testing mandate (exhaustive, before the type is trusted)**: property-based tests over the algebraic laws (commutativity/associativity/identity/distributivity of exact ops, total order on compare, negation/abs round-trips, canonical-form preservation under every operation); boundary exhaustion around ±2^63 and 0; differential fuzzing against pure `math/big` as the reference implementation and against the Racket backend via the corpus oracle; `go test -fuzz` on the spill/normalize paths; map-key, hash, and JSON round-trip suites. Plus a focused formal review of the module, same treatment as the capability/proof runtime — it is small (a few hundred LOC) and load-bearing for everything.
   - Typed Go client stubs: JSON numbers beyond int64 range need string encoding (PosixMillis dual-encoding precedent).
   - Costs accepted: 16 bytes per Int value instead of 8; arithmetic emits as `teslrt` helper calls (trap-checked int64 would have required the same); values beyond ±2^63 pay real bignum cost — rare by construction.
   - Later optimization, not semantics: where the checker proves a value range fits int64 (or Int32), the emitter may emit bare native arithmetic with no branch.
2. **Exhaustiveness mitigation: both.** DECIDED. Emitted `default: panic("unreachable: checker guarantees exhaustiveness")` arms *and* the `exhaustive` linter in generated-code CI. The one interaction to configure: `exhaustive` treats a `default:` arm as satisfying exhaustiveness by default, which would blind it — set `default-signifies-exhaustive: false` in the lint config so the linter still checks every tag. The two layers are independent: the linter catches emitter drift statically, the panic arm contains any miss at runtime.
3. **Release build: mode-split emit.** DECIDED. Release emit generates no instrumentation at all — zero references to the debug package in emitted source — rather than build-tag stubs or runtime flags. See "Release builds" below for the full design and verification layers.
4. **Dependency exceptions: all four approved.** DECIDED. pgx, golang-jwt, go-oidc, and otel-go are the approved third-party set (provenance in the Dependency exceptions section). Email stays hand-rolled over stdlib `net/smtp`. Any future dependency beyond these four goes through the same flag-and-decide gate.
5. **Coraza: skipped for now.** DECIDED. Cheap to reverse — Coraza is plain `net/http` middleware, so the emitted middleware chain keeps the slot and adding it later is a runtime-library change plus a config flag, no architectural cost. Revisit after the port stabilizes if customer trust signals warrant it.

## Migration review incorporation (external review, 2026-08-13)

`go_migration_feedback.md` reviewed the migration and recommended continuing with Go. Its
findings are folded in here; the load-bearing one was a real correctness bug.

**Fixed — the Float key comparator (was a lookup bug, not an ordering quirk).** Dict and
Set are sorted, so their binary search derives key equivalence from the comparator:
"neither side is less" means "same key". The emitter was supplying native IEEE `<`, whose
equivalence classes are NOT `FloatEqual`'s, and both mismatches were reproduced as failing
tests before the fix:

- Every IEEE comparison involving NaN is false, so a NaN key looked equivalent to whatever
  value the search first probed. `Set.member NaN {1,2,3}` returned **true**, and inserting
  NaN was a **no-op**.
- IEEE treats `-0.0` and `+0.0` as equal while `FloatEqual` deliberately distinguishes
  them, so the two **collapsed into one key**.

`teslrt.FloatKeyLess` is now a total order whose equivalence classes match `FloatEqual`
exactly — all NaNs are one class placed before every number, `-0.0` immediately before
`+0.0` — under the law `FloatEqual(a, b) == !FloatKeyLess(a, b) && !FloatKeyLess(b, a)`,
checked exhaustively over a corpus including multiple NaN signs and payloads, infinities,
subnormals and both zeros, plus Dict lookup/replacement and Set insert/dedup/union/
intersection/difference/subset over the same values. The emitter uses it **only** on the
Dict/Set key path (a separate `ordered_key_expr`); user expressions and `List.sort` keep
plain IEEE, and a Float-backed newtype inherits the key comparator by unwrapping.

**Two more emitter bugs the same probe caught**, both invisible until a program wrote a
negative-zero literal — which no earlier probe had done:

- `-0.0` emitted `-float64(0)`, and in Go that is **positive** zero (staticcheck SA4026
  names this exactly): the negation applies to an already-typed value. Since Racket's
  `-0.0` is a real negative zero and Tesl's Float equality distinguishes the two, this was
  a wrong answer, not only a lint finding. Negation now folds into the literal.
- A literal Go has no syntax for (negative zero, infinity, NaN) renders as a `math` call,
  but `math` was never added to the emitted import list, so such a module did not compile.

**Adopted as contract — Dict and Set are UNORDERED datatypes.** Recorded in the stdlib docs
(the type entries plus `Dict.keys`/`Dict.values`/`Dict.toList`/`Set.toList`): every element
or binding appears exactly once, in unspecified order; `keys` and `values` have no promised
positional relationship (use `toList`); programs sort explicitly when order matters for
presentation, pagination, snapshots, signatures, hashing or canonical serialization.
"Unspecified" is not "randomized" — the sorted representation may keep returning its
deterministic internal order because that is free and helps logs and reproducibility, but
it stays an implementation detail so a future HAMT or tree needs no language change. If
ordered traversal becomes a recurring need, add `toSortedList` or an ordered collection
type rather than changing the base contract.

**Recorded — the generated-Go trust boundary.** Tesl's guarantees hold while developers
interact through Tesl code and supported Tesl runtime boundaries; they do not survive
hand-editing the emitted Go. Under that contract deeply immutable Go representations are
unnecessary, and defensive copies on every read are rejected: they would cost real
allocation and traversal without strengthening the supported interface. What the trusted
implementation must uphold instead: writers allocate, readers may alias, record updates
produce new values, `teslrt.Int` clones at ownership boundaries, and every future boundary
(HTTP, JSON, SQL, queues, FFI) must take ownership or copy when external mutable storage
enters the Tesl value graph and must never expose a pooled or later-reused buffer as a
Tesl value. Nil and empty collections need normalising where the distinction would
otherwise leak through Go codecs. Exported Go fields and raw slices are acceptable under
this model.

**Accepted as gates before Racket retirement** (not yet done): fold complexity — a scalar
`foldl`/`foldr` with an O(1) callback must be O(n), and the canonical builder folds
(list reconstruction via `foldr`+`append`, `Set.insert` from `Set.empty`, `Dict.insert`
from `Dict.empty`) must lower to private builders that allocate once rather than emitting
repeated copy-on-write calls, which are Θ(n²) time and allocation volume; emitted-shape
tests plus n/2n/4n scaling and allocation benchmarks; and an escape/linearity condition, so
a builder optimisation only ever mutates fresh state that no earlier accumulator value can
observe. Also gating: mutual tail recursion (still plain Go recursion, so deep mutual
recursion can hit an unrecoverable stack overflow), general curried function values, one
end-to-end HTTP/JSON/pgx service with cancellation and concurrency, debugger parity, and
differential runs that compare membership/bindings rather than incidental list order for
unordered collections.

## Migration path

1. Lift the pure-logic stdlib modules into Tesl (see "Pre-migration" above) — this is useful on its own and can start immediately. (An earlier step 0 — retrofitting checked-int64 semantics into the Racket backend — was deleted when the Int decision was revised to the hybrid representation; no semantic change ships in the current product.)
2. ~~Settle the dependency exceptions~~ — done 2026-08-04, all four approved (see "Dependency exceptions").
3. `emit_go.ml` behind a flag; Racket stays the reference backend. Toolchain gates (vet/staticcheck/gosec/golangci-lint) wired into CI from the first emitted program, not retrofitted. Release/debug mode split (see "Release builds") designed in from the start. The hybrid `teslrt.Int` type and its full test suite (property-based + fuzz + formal review, per the Decisions mandate) land first, before any emit code depends on arithmetic.
4. Migrate/port the test estate per "Test migration and parity" — backend-agnostic suites run against both backends from day one; Go unit tests land with each ported module. Port built-in mutation execution in this phase too; its AST operators remain shared and each backend owns compile/test execution.
5. **Differential corpus testing**: run the entire `.tesl` corpus (`compile-examples.sh`, `tests/*.tesl`, plus the lifted stdlib `.tesl` modules) through both backends and diff observable behavior — the existing ratchet suite becomes a cross-backend oracle, run under `-race` on the Go side. This is the main defense against the long tail of parity bugs (float formatting, string/unicode, JSON edges).
6. Port runtime lib by lib, capability/proof runtime with its own focused security review. Runtime hardening defaults land here as each subsystem ports.
7. Debugger and api-test instrumentation last, against the parity checklist (requirement 3).
8. Retire the Racket backend only when the corpus diff has been empty across the full suite for an extended period, test coverage parity is documented, and the debug-parity checklist is fully green.

| `List` as a Go slice + `Tesl.List` leaves | Implemented, 14 non-higher-order leaves | **Representation decision: `List a` is `[]T`**, chosen for idiomatic, readable emitted code (the eject argument) over a persistent cons list. Immutability then becomes the runtime's job — but only partly, and the precise rule matters (maintainer, 2026-08-12):

> **Only writers allocate. Readers may alias.**

Nothing in a Tesl program can mutate a list, so aliasing is observable *only* if a function inside `internal/teslrt/list.go` writes into a backing array another live Tesl value can still see. That makes `Take`/`Drop`/`Tail` plain O(1) sub-slice views, while the writers (anything append-like, plus `SortBy`, which sorts in place) build a fresh array first. The dangerous combination is a zero-copy view PLUS a capacity-reusing append — `append(xs[:2], v)` writes index 2, which a longer live value still sees — and since both halves live in that one file, forbidding capacity reuse in the writers is sufficient; copying in the readers would be redundant. The test asserts the behavioral property ("did any live value change?") rather than the representation, and separately pins that readers really are views, so a later "defensive copy" cannot silently reintroduce O(n) reads. Any list writer added later must honour the same rule.

**Views are bounded, because a slice pins its whole backing array.** `List.take 1` of a 10,000-row query result would otherwise hold all 10,000 rows for as long as that one-element value stays reachable — a real cost on a DB path, since the array is freed only when no slice points into it. (`List.head`/`List.last` are unaffected: they copy an element value out.) So past a 32-element slack, a view may retain at most twice its own length and otherwise copies. That copy costs O(len(result)) — by construction less than half the memory it releases — so it can never turn a cheap read into an expensive one: a 1-element take copies one element, while a `drop 1` of a huge list keeps aliasing, where copying would cost as much as it saved.

One consequence remains, accepted deliberately: this is an invariant of the *runtime*, not of emitted module code — a Go author who sheds Tesl and appends to a `Take` result reintroduces the classic aliasing bug, which is out of scope by design rather than paid for with O(n) on every read.

Tesl **does** have lambdas — `fn(x: Int) -> body` in expression position — and they are the dominant form at these call sites (31 `List.map (fn(…))` in the corpus against the named-function style; 116 lambda uses overall). That makes the loop plan better rather than worse, in three tiers:

- **Lambda argument** — inline the body straight into the generated loop. No closure is allocated, no call happens at all, and captures need no special handling because the loop sits in the same scope the lambda was written in.
- **Named function argument** — the same loop with a direct, inlinable call.
- **Function *value*** — the general case, and NOT a corner: lesson36 is a whole lesson on it. Lambdas are real closures (captured, `let`-bound, passed, returned) and Tesl functions are **curried, with partial application free** — `let addFive = fn(x: Int, y: Int) -> x + y; addFive 5` yields a closure expecting one more `Int`. So this tier needs `TFun` → Go `func(A) B` *plus a calling-convention decision*: Go functions are not curried, so a partially applied Tesl function has to become an explicitly emitted closure, and every function used as a value needs a consistent shape (fully-applied direct call vs. curried value form). The emitter's current "requires a fully-applied call" rejection is the honest boundary until that decision is made — and it should be made deliberately, because it touches every call site, not just list operations.

Output allocates once at exact length (`make([]U, len(xs))`, filled by index) rather than growing with `append`. **Equality and ordering are passed in as closures** — a generic Go function cannot compare a `T` (`teslrt.Int` is deliberately non-comparable), but the emitter knows the concrete element type at every call site, so it emits `teslrt.ListMemberBy(x, xs, func(teslX, teslY teslrt.Int) bool { return teslrt.Equal(teslX, teslY) })`. Both counts carry an `IsNonNegative` proof that erases, so the runtime check is containment, not the enforcement; a count that cannot be allocated panics with a clear message rather than truncating to a wrong-length list. Semantics were taken from `tesl/list.rkt`, NOT the lifted `tesl/list.tesl` — **the lifted `range`/`repeat` bodies there are truncated stubs** (`range start end = if start < end then [start] else []`, one element), which never ship because `list.rkt` imports exactly 16 lifted names with `only-in` and defines these two natively.
